# Meaningful validation

Use these rules when selecting or adjudicating a concrete task's testing methodology, reviewing proposed test scope, or assessing validation evidence. Each concrete task selects its own methodology. An epic may describe shared outcome-level validation, but need not select a methodology before architecture and does not impose one on children.

## Canonical test strategy (TEST-01–06)

- **TEST-01 — Behavior:** Trace tests to requested behavior and user stories. Assert externally observable outcomes and preserve meaningful coverage; do not use ordinary behavioral tests to require source/test-file hashes, review receipts, or orchestration approval flags as bookkeeping. Hashes remain valid for genuine product behavior, data-preservation assertions, or justified external-tool integrity requirements.
- **TEST-02 — Work-type strategy:** Unless the user directs otherwise, for established behavior changes and reproducible bugs write behavioral tests and show meaningful red before the fix when practical; compile, setup, or environment failures are not meaningful red. For refactors, run a passing behavioral baseline and add passing characterization coverage for material gaps. For greenfield projects or genuinely new components, test-first is optional, but meaningful coverage is required before acceptance. Documentation-only work needs accuracy/consistency review, not artificial tests. For operational resource/configuration changes, use proportionate rendering or behavioral verification; deployment evidence is required only when agreed or needed to establish the specified outcome. Do not manufacture a failing application test for a configuration-value change.
- **TEST-03 — Stable contracts and test cleanup:** Prefer stable observable contracts over implementation details. Exact string or byte comparisons are appropriate only when exact representation is itself contractual. Diagnose test/fixture failures before changing expectations; never weaken meaningful assertions merely to get green. For test-only cleanup, evaluate the reason and retained behavioral coverage; remove assertions shown to cover only non-behavioral provenance/bookkeeping when explained, while preserving meaningful behavior coverage. Test deletion does not require an artificial failing-red demonstration.
- **TEST-04 — Scope before work:** Unless the user directs otherwise, before authoring or running tests, changing/removing executable test coverage, or implementing applicable behavioral work, the worker proposes proportionate test scope and invokes exactly one `test-scope-reviewer` subagent for an initial scope-only assessment. A behavioral change cannot claim the no-test-scope exemption merely because the proposal contains no tests; the reviewer must assess that omission. For test cleanup, the proposal includes the removal rationale and retained behavioral coverage, which the same initial review vets before edits; deletion does not require an artificial red run. Skip invocation only for documentation-only work or work that genuinely changes no relevant behavior and has no test scope to vet. The reviewer loads `ponytail` and this skill, checks the proposal against the current task methodology and latest user direction, and returns actionable findings with a conclusive `PASS` or `REVISE`; it does not run tests, edit code, perform discovery, or approve delivery. Address necessary feedback before proceeding and escalate unresolved behavior or scope decisions. If the child cannot be invoked, fails, is unavailable, or returns no conclusive result, stop and report the blocker unless the user has directed that testing/review requirement be dropped; do not substitute another review path or repeat the embedded review. Do not repeat this review for later edits.
- **TEST-05 — Diagnose failures:** Classify failures as product behavior, test/fixture, environment, or evidence failures. Repair tests/fixtures only after diagnosis and preserve relevant behavioral assertions; distinguish unrelated pre-existing failures and rerun affected checks after corrections.
- **TEST-06 — Honest evidence:** Report criterion-level evidence from the delivered revision, exact checks/results, limitations, and QA status. Never report an unrun, blocked, or inconclusive check as passed. A clear user direction may change or drop any testing methodology or testing requirement at any time, without special waiver wording or ceremony; the controller communicates the current direction to affected workers/reviewers, who proceed accordingly. Checks dropped by current user direction are no longer required, but report that they were not run. This does not alter unrelated authorization, safety, or delivery gates. Focused checks belong to workers; integration owns agreed broader checks; the paired final reviewer is static-only and assesses delivered tests for behavioral coverage and brittleness against the current task methodology. It does not redesign the strategy. Human QA is only for judgment/access limits, with agreed steps, expected result, owner, and blocking stage.

Before implementation, agree a concise methodology and validation plan with the user for each concrete implementation task, including behavior/risks, work type, checks/owner/environment, pass criteria, limitations, and blocking stages. Record it in the existing `Validation` section for concrete Beads; for non-Bead work pass it in the worker brief without creating a Bead solely for it. A clear user direction can change or drop a testing methodology or requirement at any time without special waiver wording or ceremony; communicate the current direction and proceed, reporting what was and was not checked. Remove or weaken tests only for obsolete behavior, demonstrated redundancy, or equivalent/better replacement coverage; explain why, never merely to make checks pass. Rendering, installation, and content-preservation checks apply when executable templates or installation logic change, not to test their prose. Agents run reasonably available, reliable, safe programmatic checks. Replacing promised automation with human QA requires agreement.

Approval/considered done requires evidence against the current acceptance criteria from the delivered revision, passed checks still required by the current user direction, completed other required QA, and disclosed limitations. Not run, blocked, or inconclusive is not passed. User-directed changes to testing requirements are not a waiver ceremony; retain the actual evidence status. Other authorization, safety, and delivery gates remain unchanged. Classify pre-existing failures and selectively rerun affected checks after corrections. Workers own focused checks, integration runs broader checks when warranted, and reviewers perform static assessment only. Validate an epic's own outcome-level criteria, not just child completion. CI/branch protection and release gates are separate; these rules neither guarantee model compliance nor technically prevent direct Hub closure.
